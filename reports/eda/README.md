## 2. Как воспроизвести

Из корня репозитория:

```bash
uv sync
# синтетика (≈ 4 с) и тесты генератора и метрик
uv run python -m dd_verifier.synth --config configs/synth.yaml --out data/synthetic
uv run pytest -q
# реальный прокси биллинга (≈ 2,5 мин: скачивание + parquet)
uv run python scripts/fetch_online_retail.py
# корпус SEC: нужен контакт в User-Agent (правило fair access SEC); задаётся только переменной окружения
SEC_USER_AGENT="Имя Фамилия e-mail" uv run python scripts/fetch_sec_claims.py
# ноутбуки (графики пишутся в reports/figures/)
uv run jupyter nbconvert --to notebook --execute --inplace notebooks/01_eda_sec_claims.ipynb
uv run jupyter nbconvert --to notebook --execute --inplace notebooks/02_eda_billing_proxy.ipynb
uv run jupyter nbconvert --to notebook --execute --inplace notebooks/03_eda_synthetic_dataroom.ipynb
```

Ноутбуки 01 и 03 работают офлайн: частоты терминов SEC и список проспектов лежат в `data/reference/`. Если файла
частот нет, ноутбук 01 запросит их у efts.sec.gov (21 запрос, ≤ 4 в секунду, общий User-Agent). Сравнение с
корпусом предложений SEC в ноутбуке 03 включается само, когда появится `data/reference/sec_kpi_claims.csv`.

## 3. Главные находки

1. **Определение и очистка меняют KPI сильнее любых допусков P5.** На реальной выгрузке наивная выручка за 12 месяцев
   в 1,12 раза больше очищенной (в 1,32 раза — если считать только по известным клиентам), а число клиентов
   различается в 2,6 раза: 4 331 «покупали за год» против 1 665 «активны в последнем месяце».
   → [02_kpi_waterfall](../figures/02_kpi_waterfall.png), [02_customer_count_definitions](../figures/02_customer_count_definitions.png).
   Отсюда расчёт каждой метрики в стандартном варианте и в варианте компании (R4).
2. **Отмены в реальной выгрузке не привязаны к исходному счёту и уходят в другой месяц.** 15,5% инвойсов — отмены
   (7,1% валовой выручки), две трети частичные, медианный лаг 10 дней, 48% попадают в другой календарный месяц.
   → [02_cancellation_lag](../figures/02_cancellation_lag.png). Правило отнесения кредит-нот к месяцу зафиксировано
   в библиотеке метрик: по периоду услуги.
3. **Пустой id клиента — проблема уровня целого инвойса и меняется во времени.** В ритейле 16,3% инвойсов и 15,1%
   выручки без клиента, по месяцам от 8,5% до 30%. → [02_missing_customer_monthly](../figures/02_missing_customer_monthly.png).
4. **Даже 1% пустых id ломает удержание.** В синтетике 1% подписочных инвойсов без `customer_id` сдвигает GRR/NRR до
   −2,9 п.п. (5-й перцентиль; порог P5 — 2 п.п.) и меняет эталонный вердикт у 1,6% утверждений; при 0,2% — у 0,2%.
   → [03_missing_id_sensitivity](../figures/03_missing_id_sensitivity.png). В системе доля выручки без клиента должна
   понижать уверенность клиентских метрик. Эталон значения для гейта G1 — `true_value_observed` (расчёт по файлам
   «как пришли»): против значения на чистых таблицах даже идеальная система совпала бы только в 61 из 68 случаев (03 §4.5).
5. **Шум синтетики откалиброван по реальному прокси.** Дубли 0,55% (цель 0,5%), void 1,05% (цель 1%), кредит-ноты
   3,6% строк (цель 3%, включая посаженные D04/D09). Не реализованы частичные кредит-ноты, перекрытие выгрузок,
   служебные строки, неполный месяц. → [03_quality_vs_proxy](../figures/03_quality_vs_proxy.png).
6. **Платежи за внедрение есть у всех: «ARR с внедрением» выше стандарта на 9–24% в каждой dev-компании**, включая
   две, где D01 не посажен. Флаг нельзя ставить по факту «вариант больше стандарта»: вердикт даёт P5 по стандартному
   определению, а каким определением получено заявленное число — это объяснение. → [03_definition_gap](../figures/03_definition_gap.png), [03_arr_trajectories](../figures/03_arr_trajectories.png).
7. **Таблица когорт компании обманывает только там, где в неё встроено определение.** У четырёх dev-компаний
   `cohorts.xlsx` совпадает с инвойсами (NRR ±1 п.п.), у Pantrio (D06, «только выжившие») NRR по таблице 105,8% против
   78,0% (+27,8 п.п.). Бейзлайн B1, читающий таблицу, на D06 будет обманут. На слайдах без текста (2 из 13 в каждом
   деке) утверждений нет — FR2 на синтетике не проверяется. → [03_cohorts_vs_ledger](../figures/03_cohorts_vs_ledger.png).
8. **Классы несбалансированы, holdout маленький.** Красных флагов 26% в dev (26 из 99 в 5 классах) и 29% в holdout
   (56 из 193); `SUPPORTED` — 61% и 59% от 5 классов; `UNVERIFIABLE` — 2 и 8. Семейство — одно наблюдение: флагов-семейств
   20 в dev и 42 в holdout. При recall 0,90 интервал Уилсона на 42 семействах — [0,77; 0,96]; для ±0,05 нужно ≈140
   семейств-флагов, т. е. ≈33 компании. Решения — по recall и precision флагов, macro-F1 — только для сводки.
   → [03_verdict_balance](../figures/03_verdict_balance.png), [03_claims_by_case](../figures/03_claims_by_case.png).
9. **Зона у порога P5 пустая.** Все `SUPPORTED` отклоняются не больше чем на 0,36 нижнего порога, все `EXAGGERATED` —
   не меньше чем на 1,67 порога; в интервале 0,4–1,6 нижнего порога нет ни одного утверждения. Различение
   «округление или завышение на 4–7%» офлайн не проверяется (риск R3). → [03_delta_zones](../figures/03_delta_zones.png).
   Ошибка генератора v0.1 исправлена: D09 подавал устаревшее значение в любую сторону, и 5 из 6 занижений среди
   числовых флагов dev были D09. Сейчас занижение одно (D08, 293 клиента при 380).
10. **Денежным метрикам хватает инвойсов и курсов; клиентским нужен `customer_id` и даты справочника; метрикам вне
    онтологии нужны затраты, которых в data room нет.** `NOT_ENOUGH_DATA` в синтетике бывает от нехватки истории
    (NRR на дату, когда когорте нет 12 месяцев), а не от отсутствия таблицы. → [03_metric_data_matrix](../figures/03_metric_data_matrix.png).
11. **Реальные названия метрик разнообразнее синтетики.** В проспектах ПО (SIC 737x) у NRR 5 названий (32–223
    документа на каждое, самое частое — меньше трети упоминаний), у GRR — 3; «customer churn» в 13 раз чаще
    «logo churn». В синтетике NRR названа двумя способами. Экстрактор SEC узнаёт KPI в 39% из 72 числовых
    утверждений dev. → [01_terms_by_industry](../figures/01_terms_by_industry.png), [03_sec_vs_synth_terms](../figures/03_sec_vs_synth_terms.png).
12. **Термины вне онтологии в общеотраслевых счётах завышены.** «Lifetime value» — 1 200 документов во всех
    отраслях, но в проспектах ПО только 321 (27%); «ten largest customers» — 134 и 23 (17%). Для SaaS-выводов
    берём только SIC 737x. → [01_terms_by_industry](../figures/01_terms_by_industry.png).
13. **Все 11 типов расхождений, кроме D09, имеют реальный аналог**, но реальные завышения кратные (×2–×10), а каталог
    смещён к тонким расхождениям через определения. → [`docs/real_world_cases.md`](../../docs/real_world_cases.md).

## 4. Риски данных и ответ дизайна

| Риск (находка) | Где видно | Ответ в дизайне |
| --- | --- | --- |
| Синтетика проще реальности: документы ~650 слов на компанию, однообразные названия метрик, нет части шума (R2) | 01; 03 §1, §8; 02 §11–12 | улучшения генератора (03 §9): синонимы метрик по SEC, периоды «as of», частичные кредит-ноты, перекрытие выгрузок; ретро-пилот на реальных сделках |
| Dev и holdout рендерятся из одних шаблонов → holdout меряет запомненные формулировки | 03 §9 | отдельный пул шаблонов и синонимов для holdout v1; recall извлечения отдельно для «знакомых» и «новых» шаблонов |
| Генератор и детектор пишет один автор → «сажает» то, что ловит (R3); пустая зона у порога; D06 не даёт `EXAGGERATED` | 03 §5, §6 | закрытый holdout; пограничные hard negatives (δ 3–5%) и D01–D05 с разрывом 5–8%; аудит синтетики вторым человеком и моделью другого семейства с независимым пересчётом метрик вне `src/dd_verifier` |
| Пустой `customer_id` занижает клиентские метрики | 02 §5; 03 §4.3, §4.5 | проверка качества «доля выручки без клиента по месяцам» → пониженная уверенность для NRR/GRR/churn/клиентов (порог ~2% выручки); стресс-компания в генераторе |
| Кредит-ноты без ссылки и через границу месяца | 02 §4 | признание по периоду услуги, курс — месяц начала услуги; правило записано в онтологии и в SQL-следе каждого расчёта |
| Перекрытие и дубли выгрузок | 02 §1, §6 | дубль `invoice_id` в разных файлах — проверка качества; точные дубли помечаются и удаляются загрузчиком с записью в след |
| Компании по-разному определяют метрики (R4) | 01; 02 §10; 03 §3, §3.1; real_world_cases | расчёт в стандартном варианте и в варианте компании; поиск определения в меморандуме (BM25); пометка «определение отличается» |
| Маленький holdout, широкие интервалы | 03 §5 | метрики по семействам; кластерный бутстреп и перестановочный тест по компаниям; при широких интервалах добавлять компании, а не утверждения |
| Занижение классифицируется как `CONTRADICTED` | 03 §6 | вопрос заказчику по P5 (3.4 дизайн-документа): отдельная пометка для занижений или исключение из recall флагов |
| Ритейл ≠ SaaS: нет периода услуги, предоплаты, реселлеров | 02 §11 | из прокси берём структуру проблем и порядок величин, а не частоты; поздние инвойсы — экспертная оценка |

## 5. Чего не хватает и как получить

| Чего не хватает | Сколько нужно | Как получить |
| --- | --- | --- |
| Корпус реальных KPI-предложений SEC (вторая часть EDA 01) | ~50 проспектов, ~60 запросов, кэш ~150 МБ; разметка 60 извлечённых + 30 отклонённых предложений для оценки экстрактора | автор задаёт `SEC_USER_AGENT="Имя e-mail"` (только в окружении) и запускает `scripts/fetch_sec_claims.py`; затем раздел по предложениям в ноутбуке 01 и пересчёт раздела 8 ноутбука 03 |
| Реальные data room | 5–10 закрытых сделок фонда | ретро-пилот (1.2 дизайн-документа) под NDA, в закрытом контуре |
| Реальный SaaS-биллинг (период услуги, предоплата, реселлеры, поздние счета) | 1–2 выгрузки | у фонда или портфельной компании под NDA; до этого — экспертные значения в `noise:` |
| Более узкие интервалы на holdout | для recall 0,9 ± 0,05 нужно ~140 семейств-флагов, при 4,2 на компанию — ~33 holdout-компании вместо 10 | сгенерировать новые компании по тому же каталогу (дёшево); правило протокола: holdout не переиспользуется после G1 |
| Реальные формулировки деков (не проспектов) | 20–30 публичных деков Seed–Series A | открытые коллекции деков; проверить лицензию перед использованием |
| Независимая проверка синтетики | 3 компании полностью + выборка утверждений | второй человек и модель другого семейства (протокол оценки, 2.1) |
