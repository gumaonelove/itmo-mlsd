# Данные проекта DD Verifier (data card)

Документ описывает все данные проекта: синтетический data room (раздел 1) и реальные публичные датасеты,
по которым калибруется синтетика и проверяются формулировки утверждений (раздел 2).

| Каталог | Что лежит | В git |
| --- | --- | --- |
| `data/synthetic/` | синтетический data room 15 компаний: dev (5) и holdout (10) | нет, генерируется командой ниже |
| `data/external/` | выгрузки реальных датасетов (SEC EDGAR, UCI Online Retail II) | нет, скачиваются скриптами из `scripts/` |
| `data/reference/` | небольшие производные корпуса для воспроизводимого EDA | да |

---

## 1. Синтетический data room

### 1.1. Зачем и откуда

Реальные data room закрыты NDA, поэтому MVP проверяется на синтетике (допущение P2 дизайн-документа).
Генератор строит для каждой компании:

- биллинг и справочник клиентов с **известными** истинными метриками;
- документы на английском (дек, 1–3 пресс-релиза, меморандум CFO) с утверждениями;
- эталонную разметку: для каждого утверждения — точная цитата, место в документе, истинное значение и вердикт.

Расхождения «сажаются» по каталогу `configs/discrepancy_catalog.yaml`, который зафиксирован до разработки
пайплайна. **Эталонные вердикты не назначаются вручную**: генератор считает их библиотекой метрик
(`src/dd_verifier/metrics`) и правилами допусков P5 на чистых данных и падает, если посаженный случай
не дал ожидаемого вердикта. Поэтому эталон и система используют один код: ошибку в функции метрики или в P5
офлайн-оценка не увидит. Защита — аудит с независимым пересчётом метрик вне `src/dd_verifier` (этап 3 в 2.3
дизайн-документа).

Как воспроизвести (≈ 4 с на ноутбуке):

```bash
uv run python -m dd_verifier.synth --config configs/synth.yaml --out data/synthetic
uv run pytest -q   # в т.ч. инварианты генератора
```

Генерация детерминирована: у каждой компании свой seed (`numpy.random.Generator`), распределение
случаев каталога задаётся `assignment_seed`. Одинаковый конфиг даёт побайтно одинаковые файлы
(sha256 каждого файла — в `manifest.json`).

### 1.4. Схемы таблиц

**customers.csv** — справочник клиентов (снимок на конец истории).

| Колонка | Тип | Значение |
| --- | --- | --- |
| customer_id | str | `C00001`…; записи-дубли (шум) получают новые id |
| customer_name | str | название организации с юр. формой (Inc., LLC, Ltd, GmbH, B.V., SAS) |
| segment | SMB / MidMarket / Enterprise | сегмент; SMB — «малые» клиенты для варианта churn компании |
| country | US / GB / DE / FR / NL / ES / IE | страна; задаёт валюту счетов |
| channel | direct / reseller | канал продажи |
| signed_date | date | дата подписания контракта |
| go_live_date | date, может быть пустой | запуск; пусто — пилот или ещё не запущенный клиент |
| churn_date | date, может быть пустой | первый день без услуги (всегда 1-е число месяца) |
| is_pilot | bool | бесплатный пилот: без go-live и без инвойсов |

**invoices.csv** — выгрузка биллинга.

| Колонка | Тип | Значение |
| --- | --- | --- |
| invoice_id | str | `INV-<префикс>-000001` |
| customer_id | str, может быть пустым | пусто — дефект выгрузки (шум) |
| issue_date | date | дата выставления (может быть позже начала услуги) |
| service_period_start / service_period_end | date | период услуги; выручка признаётся равномерно по месяцам периода |
| amount | float | сумма в валюте счёта; у кредит-нот отрицательная |
| currency | USD / EUR / GBP | валюта счёта |
| payment_type | subscription / one_time / implementation | подписка, разовый платёж (обучение), внедрение |
| status | paid / open / void / credit_note | void исключается, credit_note вычитается |
| reseller_fee | float | доля реселлера (gross-модель): net = amount − reseller_fee; у прямых клиентов 0 |

**fx_rates.csv** — `month` (YYYY-MM), `currency`, `usd_rate` (USD за единицу валюты). Суммы переводятся
по курсу месяца начала периода услуги.

**cohorts.xlsx** — лист `cohort_mrr`: подписочный MRR (USD) по месяцу go-live × месяцу; лист `notes`:
определение компании. У компаний со случаем D06 таблица построена «по выжившим» (ушедшие клиенты удалены).

**documents/** — английский текст в Markdown. Дек: 13 слайдов с фиксированной структурой
(Customers — слайд 6, Traction — 7, Retention and unit economics — 8, Outlook — 11, Team and recognition — 12);
слайды 5 и 9 помечены `<!-- image-only -->` (картинка без текстового слоя, утверждений там нет).
Пресс-релиз: блоки через пустую строку, блок 1 — заголовок, блок 2 — дейтлайн. Меморандум CFO: 5 страниц
(1 — вводная, 2 — признание выручки, 3 — ARR и MRR, 4 — клиенты и churn, 5 — retention).

**gold/claims.jsonl** — одно утверждение на строку.

| Поле | Значение |
| --- | --- |
| claim_id | `<company_id>-NNN` |
| family_id | одно и то же утверждение в деке и пресс-релизе (семейство) имеет общий family_id |
| doc, location | файл и место: `{"slide": N}` для дека, `{"paragraph": N}` для пресс-релиза (номер блока с 1) |
| quote | **точная подстрока** документа (буллет или предложение) |
| claim_type | level / growth / share / count / customer_mention / out_of_ontology / forecast / factual |
| metric_id | id метрики онтологии или null; рост уровня другой метрики — `claim_type=growth` + id этой метрики |
| claimed_value | число из текста в единицах онтологии: USD; множитель для роста («+160%» → 2.6); доля для share (4.5% → 0.045); имя клиента для customer_mention |
| unit | USD / x / share / customers / months / null |
| period_start, period_end | YYYY-MM: база роста, первый месяц периода (выручка, churn), месяц когорты (NRR/GRR); period_end — дата значения |
| qualifier | exact (null) / more_than / about / less_than |
| case_id | D01–D11, H01–H04, N01, N02, U01, F01 или null для обычного верного утверждения |
| company_variant | вариант определения, которым посчитано заявленное число (например, incl_one_time), `stale_period` для D09 |
| true_value_standard | значение по стандартному определению (null, если не считается) |
| true_value_company_def | значение по определению компании (для D09 — устаревшее значение) |
| delta | сырое отклонение заявленного от стандарта: относительное для level/count/growth, в п.п. для share. **Квантификатор не учитывает**: у «120+» при 127 — −5,5% при вердикте SUPPORTED |
| delta_p5 | δ по правилу P5: 0, если «более / менее N» выполнено; иначе равно `delta` (отклонение от N). Для порогов и графиков берите это поле |
| gold_verdict | SUPPORTED / EXAGGERATED / CONTRADICTED / NOT_ENOUGH_DATA / UNVERIFIABLE / FACTUAL_OUT_OF_SCOPE (последний не входит в 5-классовые метрики) |
| true_value_observed | то же значение по стандартному определению, но по файлам «как пришли» после загрузчика (`load_data_room`: минус точные дубли). **Эталон для точности значений (G1)**: система видит только эти файлы. null для нечисловых |
| noise_sensitive | true, если вердикт по файлам «как пришли» отличается от `gold_verdict` (шум сам меняет вердикт); такие утверждения отчитываются отдельно |

**gold/truth_monthly.csv** — по месяцам истории: mrr, arr, revenue (за месяц), active_customers,
new_customers, churned_customers, logo_churn (за месяц), nrr_12m, grr_12m, acv, top10_concentration_12m.
Все — стандартные определения на чистых данных; пусто, если для метрики не хватает истории.

**manifest.json** — версия генератора, seed, хэш конфига компании, sha256 каждого файла, число строк
(«грязных» и чистых), назначенные и реально посаженные случаи, журнал калибровки и посадки
(масштабы, окна, суммы кредит-нот), счётчики шума и `dirty_vs_clean` — id утверждений с `noise_sensitive = true`
(сейчас 0 в dev и 0 в holdout). Это отчёт, а не условие генерации: подбирать шум или seed под нулевое число
расхождений нельзя, иначе holdout становится чище реальности.

### 1.5. Какие данные нужны для какой метрики

Из `configs/ontology.yaml` (поле `required_data`). Это же определяет, когда утверждение получает
`NOT_ENOUGH_DATA`: нужной таблицы нет или период не покрыт выгрузкой.

| Метрика | customers | invoices | fx_rates | История |
| --- | --- | --- | --- | --- |
| mrr, arr | — | период услуги, сумма, валюта, тип, статус, reseller_fee | да | месяц m (peak_month — 12 мес.) |
| arr_growth | — | то же | да | оба конца периода (trough_base — всё окно) |
| revenue | — | то же | да | все месяцы периода |
| active_customers | signed / go-live / churn, is_pilot | + customer_id | да | месяц m |
| logo_churn | + segment, is_pilot | + customer_id | да | период + месяц до него |
| grr, nrr | go-live, churn | + customer_id | да | m и m − 12 |
| acv | go-live, churn | + customer_id | да | месяц m |
| top10_concentration | — | + customer_id | да | 12 месяцев |
| CAC payback, LTV/CAC, gross margin, burn multiple | вне онтологии: нет данных о затратах, COGS, денежном потоке | | | → NOT_ENOUGH_DATA |

### 1.6. Как генерируются данные

1. **Симуляция клиентов** (`synth/simulate.py`). Число активных платящих клиентов идёт по траектории
   `active_path`. Отток детерминирован по количеству: `churn.total × активные` в месяц, из них
   `churn.core` — для не-SMB; поэтому фактический churn воспроизводит заданный, а вариант
   «без SMB и пилотов» — заметно ниже. Годовые клиенты уходят только в конце оплаченного года.
   Цены — логнормальные по сегментам, в валюте клиента; допродажи и сокращения у помесячных клиентов,
   индексация при продлении у годовых. Новые клиенты платят за внедрение (распределено по 1–3 месяцам
   онбординга), иногда за обучение. Есть бесплатные пилоты и подписанные, но не запущенные клиенты.
2. **Масштаб**. Все суммы линейно масштабируются под целевой стандартный ARR на 12.2025 (`arr_end`).
   Pantrio калибруется в двух точках (см. 1.8).
3. **Посадка расхождений в данные** (`synth/plant.py`), размер эффекта задан целевым разрывом
   варианта компании и стандарта (обычно 10–18%, чтобы попасть в зону EXAGGERATED с запасом на округление):
   D01 — масштаб платежей за внедрение; D02 — разовая месячная «сезонная надстройка» к подписке
   (пик MRR); D03 — дополнительные пилоты; D04 — SLA-кредит-ноты в начале окна (провал MRR);
   D05 — ставка комиссии реселлера; D11 — сезонное сокращение подписки в квартале 2025
   (или сезонные скидки кредит-нотами, если помесячных клиентов мало); D09 — скидки кредит-нотами части
   клиентов старой когорты в последние 3 месяца, чтобы NRR/GRR на конец года были на 3–4,5 п.п. ниже лучшего
   значения 6–12 месяцев назад (отдельный поток случайных чисел, остальные посадки не сдвигаются).
   Утверждение D09 берёт только прошлое значение в пользу компании (с учётом направления метрики).
4. **Утверждения** (`synth/claims.py`). Случаи каталога распределяются по компаниям автоматически: каждый
   id — минимум 1 раз в dev и 2 раза в holdout (проверяется), D01/D02/D05 (разные определения ARR)
   и D04/D11 не совмещаются в одной компании, D05 — только при доле реселлеров ≥ 35%. Затем добавляются
   8–12 обычных верных утверждений (ARR, выручка, клиенты, NRR/GRR, churn, ACV, концентрация,
   значения на конец прошлого года, упоминания крупных клиентов). Заявленное число — ровно то, что
   написано в тексте после естественного округления; формулировки разнообразны: «3x», «+160%»,
   «more than doubled», «120+», «over 105%», «below 2.5%», «~$1.3M», «$1.65 million».
5. **Эталон**. `evaluate_claim` (та же функция, что в процессе B) считает вердикт на чистых данных;
   генератор проверяет, что вердикт входит в `allowed_verdicts` случая, а обычные утверждения — SUPPORTED.
   После наложения шума тот же расчёт по файлам «как пришли» даёт `true_value_observed` и `noise_sensitive`.
6. **Документы** (`synth/documents.py`). Около 40% утверждений повторяются в пресс-релизе другой
   формулировкой (семейство). Меморандум раскрывает определение компании (D01, D05, D06, D07),
   даёт намёк (D01, D03, D06) или стандартное определение (H04); по остальным темам — общие фразы.
7. **Шум** (`synth/noise.py`, блок `noise:` в `configs/synth.yaml`) накладывается на чистые таблицы
   после расчёта эталона; см. 1.7.

### 1.7. Шум и качество данных

Блок `noise:` откалиброван по реальной выгрузке инвойсов UCI Online Retail II (раздел 2.2,
[`reports/eda/02_billing_proxy.md`](../reports/eda/02_billing_proxy.md), раздел 12) с пересчётом с B2C-ритейла
на B2B SaaS. Проверка результата — [`reports/eda/03_synthetic_dataroom.md`](../reports/eda/03_synthetic_dataroom.md), раздел 4.

| Параметр | Было | Стало | Реальный прокси → цель для SaaS | Что делает | Влияние на метрики при правильной обработке |
| --- | --- | --- | --- | --- | --- |
| duplicate_invoice_rate | 0,4% | 0,5% | 1,13% строк → 0,5% | точные дубли строк | нет: загрузчик удаляет точные дубли |
| missing_customer_id_rate | 0,3% | **0,2%** | 16,3% инвойсов (гостевые покупки) → 1% | пустой customer_id у помесячной подписки | выручка не меняется; клиентские метрики занижаются (см. ниже) |
| void_reissue_rate | 1% | 1% | 0,9% технических строк → 1% | аннулированный инвойс рядом с корректным | нет: void исключаются |
| erroneous_invoice_credit_rate | 0,4% | 1% | 15,5% отмен → 3% кредит-нот, из них 1/3 полных | ошибочный инвойс + полная кредит-нота | нет: кредит-ноты вычитаются |
| late_issue_rate | 4% | 2% | не измеряется (одна система) → 1% (0,5–2%) | инвойс выставлен на 1–2 месяца позже | нет: признание и курс — по месяцу услуги |
| late_issue_max_months | 2 | 2 | лаг отмен p90 ≈ 80 дней | максимальный сдвиг | — |
| customer_name_case_rate | 5% | 5% | нет прямого замера | другое написание имени в справочнике | нет при нормализации имён |
| customer_duplicate_record_rate | 1% | 1% | нет прямого замера | запись-дубль клиента без инвойсов | стандарт не меняется; вариант signed_incl_pilots — чуть-чуть |

**Почему пустых customer_id 0,2%, а не 1%.** Инвойс без клиента выпадает из клиентских метрик, и клиент выглядит
ушедшим в этом месяце. При 1% GRR/NRR сдвигаются до −2,9 п.п. (5-й перцентиль 100 наложений шума; порог P5 —
2 п.п.), и эталонный вердикт, посчитанный на чистых данных, перестаёт совпадать с «грязными» файлами у 2% утверждений.
В генераторе v0.1 0,2% выбрали как максимум, при котором шум не менял эталон ни в одной из 15 компаний, — то есть с
учётом исходов holdout. Это исправлено в v0.2: условие снято, генератор пишет `noise_sensitive` и
`true_value_observed`, блок `noise:` заморожен по dev и EDA 02 и при перегенерации holdout не меняется. При 0,2%
вердикт меняется в 2% случайных наложений шума на dev (EDA 03 §4.3). Сценарий 1–5% нужен как отдельная
стресс-компания с эталоном по «грязным» данным.

**Чего из реальной выгрузки генератор пока не делает:** частичные кредит-ноты с лагом через границу месяца,
кредит-ноты без ссылки, почти-дубли с новым номером, перекрытие двух выгрузок, служебные и тестовые строки,
неполный последний месяц (список и частоты — в отчётах 02 §12 и 03 §9).

Проверки качества — `dd_verifier.data.quality.run_quality_checks` (25 именованных проверок: схема,
разбор типов, дубли строк и id, пустые и неизвестные customer_id, неизвестная валюта и пропуски курса,
доли void и кредит-нот, знак сумм, перевёрнутые периоды, многомесячные периоды, поздние инвойсы,
комиссия реселлера, варианты имён, порядок дат, запущенные клиенты без инвойсов, пилоты с инвойсами,

Holdout (по `holdout_summary.json`): 197 утверждений; SUPPORTED 114, EXAGGERATED 35, CONTRADICTED 21,

≠ SUPPORTED в 5 классах 58 (`family_verdict_counts`). Каждый id каталога посажен минимум в 2 holdout-компании.

Особенности, которые важно помнить при оценке:

- Семейство (одно утверждение в деке и пресс-релизе) — одно наблюдение: 26 флагов dev — это 20 семейств.
- D06 (NRR без ушедших) всегда даёт CONTRADICTED, а не EXAGGERATED: при оттоке 1–4% в месяц разрыв больше 5 п.п.
  Каталог допускает оба вердикта.
- D09 (устаревшее значение) в v0.2 всегда в пользу компании: генератор сажает ухудшение NRR/GRR в последние
  3 месяца (кредит-ноты старым клиентам) и берёт только «удобное» прошлое значение. Итог: EXAGGERATED в 10 из 12
  (dev + holdout). В v0.1 D09 брал прошлое значение в любую сторону и давал занижения.
- D07 даёт EXAGGERATED или CONTRADICTED в зависимости от разрыва (у Pantrio −2,44 п.п. → CONTRADICTED).

### 1.10. Что реалистично, а что нет

Реалистично:

- структура выгрузки биллинга (периоды услуги, годовая предоплата, кредит-ноты, void, валюты, комиссия реселлера);
- механизмы завышения — типичные для SaaS расхождения определений (см. `docs/real_world_cases.md`);
- формулировки утверждений с квантификаторами и перефразированием роста; «грязь» выгрузки.

Нереалистично или упрощено:

- документы короткие и шаблонные, без таблиц, сносок и графиков с текстом; нет PDF/PPTX — сразу Markdown;
- метрики считаются из одной согласованной выгрузки, в реальном data room данные приходят из разных систем;
- отток и рост заданы детерминированно (отток — по количеству), нет макро-шоков и миграций биллинга;
- размер посаженного эффекта выбран так, чтобы попасть в нужную зону вердикта, поэтому **граничных по числу случаев
  нет**: все SUPPORTED, включая H01–H04, лежат не дальше 0,36 нижнего порога P5, все EXAGGERATED — от 1,67
  (EDA 03 §6); H01–H04 трудные только по формулировке;
- dev и holdout рендерятся из одних шаблонов фраз и пулов имён: holdout проверяет перенос на новые данные, но не
  на новые формулировки (EDA 03 §9, п. 7);
- на слайдах без текстового слоя (по 2 из 13 в каждом деке) утверждений нет; `cohorts.xlsx` расходится с инвойсами
  только у компании с D06 (EDA 03 §3.1);
- первичные записи не фальсифицированы (P9); имена компаний и клиентов вымышлены, совпадения случайны.
